## O OWASP Top 10

O **OWASP** (*Open Worldwide Application Security Project*) é uma comunidade aberta que publica materiais gratuitos de segurança. O mais famoso é o **Top 10**: as dez categorias de risco mais importantes em aplicações web, atualizado de tempos em tempos com dados de milhares de sistemas. A versão de 2025:

| # | Categoria | Em português simples | Você viu em |
| --- | --- | --- | --- |
| A01 | Broken Access Control | Ver ou fazer o que não devia | Aula 1 (cupom, área do gerente) |
| A02 | Security Misconfiguration | Configuração insegura: modo debug ligado, senha padrão, erros detalhados | Aula 4 |
| A03 | Software Supply Chain Failures | Dependências e pacotes comprometidos ou desatualizados | Trilha de IA (pacotes inventados) |
| A04 | Cryptographic Failures | Dados sensíveis sem criptografia, senhas mal guardadas | Aula 2 |
| A05 | Injection | Texto de fora vira comando (SQL, XSS...) | Aulas 4 e 5 |
| A06 | Insecure Design | O problema está no desenho, não num bug | Aula 1 (modelagem de ameaças) |
| A07 | Authentication Failures | Login fraco, sem limite de tentativas, sem 2FA | Aula 2 |
| A08 | Software or Data Integrity Failures | Confiar em código ou dados sem verificar a origem | Aula 3 |
| A09 | Security Logging & Alerting Failures | Ninguém percebe o ataque porque não há registros nem alertas | Abaixo |
| A10 | Mishandling of Exceptional Conditions | Erros mal tratados que deixam o sistema num estado inseguro | Abaixo |

<Nota tipo="dica" titulo="Use o Top 10 como checklist de revisão">

Não precisa decorar. Ao revisar uma funcionalidade (sua, de um colega ou da IA), passe pelas dez linhas e pergunte: "isso se aplica aqui?". Já pega a maior parte dos problemas.

</Nota>

### Controle de acesso: o número 1

O caso clássico: a página do pedido é `/pedidos/42`. Um cliente troca para `/pedidos/43` e vê o pedido de outra pessoa. O sistema conferiu que o usuário **estava logado**, mas não conferiu se o pedido **era dele**.

```python-exemplo
def ver_pedido(usuario_logado, pedido_id):
    pedido = banco.buscar_pedido(pedido_id)
    if pedido is None or pedido.cliente_id != usuario_logado.id:
        raise PermissaoNegada()
    return pedido
```

A regra: **em cada requisição**, o servidor confere se **este** usuário pode fazer **esta** ação **neste** dado. Esconder o botão no front-end não é controle de acesso.

<Nota tipo="curiosidade" titulo="As regras no banco também contam">

No Supabase, as políticas de RLS (*Row Level Security*) fazem esse controle **no próprio banco**: a regra "cada cliente só lê os próprios pedidos" fica gravada na tabela. Mesmo que o código esqueça de conferir, o banco recusa. Defesa em camadas.

</Nota>

### Registros e alertas: perceber o ataque

Se alguém testar 10 mil senhas, alguém precisa **ficar sabendo**. Por isso os sistemas registram eventos importantes (logins que falharam, mudanças de permissão, acessos negados) e disparam alertas quando algo foge do normal. Sem senhas e dados pessoais no log, como você viu na aula 2.

### Erros que deixam portas abertas

Um sistema que, ao dar erro no meio de uma verificação, **libera** o acesso em vez de negar, ou que mostra a mensagem técnica inteira para o usuário, está tratando mal as condições excepcionais. Lembre do princípio da aula 1: **falhar fechado**. Na dúvida, nega, registra e mostra uma mensagem simples.

## Engenharia social: o ataque às pessoas

A forma mais barata de entrar num sistema é **pedir a senha para alguém**, do jeito certo. Isso é **engenharia social**, e o tipo mais comum é o **phishing**: mensagens falsas que imitam uma empresa conhecida para fazer a pessoa clicar, digitar a senha ou baixar algo.

<Nota tipo="analogia" titulo="Pensa assim: o falso fiscal">

Um homem de colete chega na cafeteria dizendo ser da vigilância sanitária e pede para ver o cofre "para a inspeção". Ele não arrombou nada: alguém abriu a porta para ele. O phishing é o falso fiscal digital.

</Nota>

Os sinais que se repetem:

<Passos itens={[
  { icone: "⏰", titulo: "Urgência", texto: "sua conta será bloqueada em 2 horas" },
  { icone: "🔗", titulo: "Link estranho", texto: "githuh.com, g1thub-login.net" },
  { icone: "🔑", titulo: "Pede segredo", texto: "senha, código do 2FA, token" },
  { icone: "🎁", titulo: "Bom demais", texto: "você ganhou, vaga garantida" },
]} />

- **Empresas sérias não pedem senha nem código de verificação** por mensagem, e-mail ou ligação.
- **Desconfie da urgência**: ela existe para você não pensar.
- **Não clique: digite o endereço** oficial no navegador ou use o app.
- **Confira com outra pessoa** por outro canal ("você mandou mesmo esse Pix?").
- **O 2FA com app ou chave física** segura muitos desses ataques, porque a senha sozinha não basta.

<Nota tipo="cuidado" titulo="Golpes que miram devs">

Há golpes feitos para quem programa: falsas vagas que pedem para você rodar um projeto "de teste" no seu computador (com código malicioso escondido), pacotes com nomes quase iguais aos verdadeiros, e mensagens fingindo ser do GitHub pedindo para "revalidar" o token. Rode projetos desconhecidos com cuidado e confira sempre a origem.

</Nota>

## O checklist do dev cuidadoso

Juntando a trilha inteira:

| Antes de entregar, confira | Aula |
| --- | --- |
| Cada requisição confere quem pode fazer o quê, no servidor | 1 e 6 |
| Senhas com Argon2 ou bcrypt, login com limite de tentativas e 2FA | 2 |
| Nenhum segredo no código, `.env` no `.gitignore` | 3 |
| Consultas com parâmetros e validação com lista de permitidos | 4 |
| Saída escapada, cookies protegidos, HTTPS | 5 |
| Dependências confiáveis e atualizadas | 6 e trilha de IA |
| Erros tratados sem expor detalhes, registros sem dados sensíveis | 6 |

<Nota tipo="ia" titulo="Revisão de segurança com IA">

Um ótimo uso da IA: *"Revise este código usando o OWASP Top 10 como checklist. Para cada categoria, diga se se aplica e se há problema."* Depois, confira cada apontamento você mesmo: a IA também erra em segurança, para mais e para menos.

</Nota>

<Explique pergunta="Por que esconder o botão 'Painel do gerente' no front-end não é controle de acesso?">

Porque o front-end está nas mãos do usuário: ele pode digitar a URL do painel direto, chamar a API com outra ferramenta ou mudar o código no navegador. Esconder o botão só melhora a interface. O controle de acesso de verdade é o servidor conferir, em cada requisição, se aquele usuário tem permissão para aquela ação naquele dado.

</Explique>
