Até agora o histórico foi uma linha reta: um commit depois do outro. Só que, no mundo real, você quer **testar ideias sem estragar o que já funciona**. Para isso existem as **branches**.

## O problema

A cafeteria está funcionando. O dono pede: "quero testar um cardápio de inverno, com chocolate quente e sopa". Se você mexer direto no cardápio principal e a ideia não agradar, vai ter que desfazer tudo. E se, no meio do teste, aparecer um erro urgente no preço do café?

<Nota tipo="analogia" titulo="Pensa assim: a panela de teste">

Na cozinha, ninguém testa uma receita nova direto no prato que vai para o cliente. O chef pega **outra panela**, faz o teste ali, prova, ajusta. Se ficar bom, junta ao cardápio. Se não, joga fora, e o prato principal nunca correu risco. Uma **branch** é essa panela de teste.

</Nota>

## O que é uma branch

Uma branch (ramo, em inglês) é uma **linha paralela** do histórico. A `main` é a linha principal, a que "vai para o cliente". Você cria uma branch, faz commits nela, e a `main` continua intacta.

```texto
main:            A ── B ── C
                            \
cardapio-inverno:            D ── E
```

Os commits `D` e `E` existem só na branch `cardapio-inverno`. A `main` continua parada no `C`.

## Criando e trocando de branch

```terminal
git switch -c cardapio-inverno
```

```saida
Switched to a new branch 'cardapio-inverno'
```

- `git switch -c nome` **cria** a branch e já **entra** nela.
- `git switch nome` só entra numa branch que já existe.
- `git branch` lista as branches. A atual aparece com `*`.

```terminal
git branch
```

```saida
* cardapio-inverno
  main
```

Agora faça mudanças e commits normalmente:

```terminal
# adicione "Chocolate quente - R$ 9" ao cardápio
git add cardapio.txt
git commit -m "Adiciona chocolate quente ao cardápio de inverno"
```

Agora a mágica. Volte para a `main` e abra o `cardapio.txt`:

```terminal
git switch main
```

O chocolate quente **sumiu** do arquivo. Ele não foi apagado: só existe na outra branch. Volte com `git switch cardapio-inverno` e ele reaparece. O Git troca os arquivos da pasta conforme a branch em que você está.

<Nota tipo="cuidado" titulo="Antes de trocar de branch, faça commit">

Se você tiver mudanças não commitadas e trocar de branch, o Git pode recusar (para não perder o seu trabalho) ou levar as mudanças junto. O hábito saudável: `git status` limpo antes de `git switch`.

</Nota>

## Juntando: git merge

O cardápio de inverno foi aprovado! Hora de levar para a `main`. A regra: **vá para a branch que vai receber** e chame o merge da outra.

```terminal
git switch main
git merge cardapio-inverno
```

```saida
Updating 9d1e0a7..4be71c2
Fast-forward
 cardapio.txt | 1 +
 1 file changed, 1 insertion(+)
```

**Fast-forward** quer dizer que a `main` não tinha nada novo desde que a branch saiu, então o Git só "avançou o ponteiro" da `main` até o último commit da branch. Simples assim.

Branch usada, pode apagar (os commits continuam na `main`):

```terminal
git branch -d cardapio-inverno
```

## Quando as duas linhas andaram

Agora o caso mais comum em equipe: enquanto você trabalhava na branch, **alguém fez commits na main**.

```texto
main:          A ── B ── C ── F
                          \
sobremesas:                D ── E
```

O merge não dá para ser fast-forward, porque as duas linhas andaram. O Git cria um **commit de merge**, que tem dois "pais" e une as duas histórias:

```texto
main:          A ── B ── C ── F ── M
                          \       /
sobremesas:                D ── E
```

Na maioria das vezes, o Git junta sozinho, porque as mudanças foram em partes diferentes dos arquivos.

## Conflitos: quando duas pessoas mexem na mesma linha

E se, na `main`, alguém mudou o preço do café para `R$ 6`, e na sua branch você mudou a **mesma linha** para `R$ 5,50`? O Git não tem como adivinhar qual está certo. Isso é um **conflito**.

```terminal
git merge promocao
```

```saida
Auto-merging cardapio.txt
CONFLICT (content): Merge conflict in cardapio.txt
Automatic merge failed; fix conflicts and then commit the result.
```

Calma. Nada foi perdido. Abra o arquivo e veja as marcações que o Git colocou:

```texto
<<<<<<< HEAD
Café coado - R$ 6
=======
Café coado - R$ 5,50
>>>>>>> promocao
Pão de queijo - R$ 6
```

- Entre `<<<<<<< HEAD` e `=======`: a versão da branch onde você está (a `main`).
- Entre `=======` e `>>>>>>> promocao`: a versão que está chegando.

<Nota tipo="analogia">

São dois cozinheiros que reescreveram a mesma linha da receita. O Git coloca as duas versões lado a lado no papel e pergunta: "qual fica?". Quem decide é uma pessoa, porque só uma pessoa sabe o que faz sentido.

</Nota>

**Resolvendo, passo a passo:**

1. Decida o resultado final. Pode ser uma das versões, as duas ou uma terceira.
2. **Apague as marcações** (`<<<<<<<`, `=======`, `>>>>>>>`) e deixe só o texto final:

```texto
Café coado - R$ 5,50
Pão de queijo - R$ 6
```

3. Salve, coloque na bandeja e finalize o merge:

```terminal
git add cardapio.txt
git commit -m "Junta a promoção do café"
```

<Nota tipo="dica" titulo="O VS Code ajuda muito">

O VS Code destaca o conflito e mostra botões: **Accept Current Change** (fica a sua), **Accept Incoming Change** (fica a que chegou), **Accept Both Changes** (ficam as duas). Depois é só salvar, dar `add` e `commit`.

</Nota>

<Nota tipo="dica" titulo="Desistir também é uma opção">

Se o conflito ficou confuso e você quer voltar ao estado de antes do merge: `git merge --abort`.

</Nota>

## Boas práticas de branch

- **Uma branch por tarefa**: `feat/cardapio-inverno`, `fix/preco-cafe`, `docs/readme`.
- **Branches curtas**: quanto mais tempo longe da `main`, maior a chance de conflito.
- **A main sempre funcionando**: nada de commit quebrado direto na `main`.
- Antes de começar algo novo, volte para a `main` atualizada e crie a branch a partir dela.

<Explique pergunta="Por que um conflito acontece, e por que o Git não resolve sozinho?">

Conflito acontece quando duas branches mudaram as mesmas linhas de um arquivo de jeitos diferentes. O Git sabe juntar mudanças em lugares diferentes, mas quando é a mesma linha ele não sabe qual versão faz sentido para o projeto. Essa decisão depende de entender o que cada mudança queria, então precisa de uma pessoa.

</Explique>

## Resumindo

- Branch é uma linha paralela: teste à vontade sem arriscar a `main`.
- `git switch -c` cria, `git switch` troca, `git branch` lista, `git branch -d` apaga.
- `git merge` junta. Se só a branch andou, é fast-forward; se as duas andaram, nasce um commit de merge.
- Conflito não é erro: é o Git pedindo para você decidir. Apague as marcações, `add` e `commit`.
