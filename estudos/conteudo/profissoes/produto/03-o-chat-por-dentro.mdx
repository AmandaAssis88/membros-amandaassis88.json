## As telas (UI/UX, front-end e mobile)

O que o usuário vê:

- **Entrar:** login com o GitHub (todo mundo aqui já tem conta!).
- **Salas:** uma lista de grupos por área (back-end, front-end, mobile...).
- **Conversa:** as mensagens, quem mandou, a hora, e o campo para escrever.
- **Perfil:** o mesmo card do mural, com avatar e frase.

UI/UX desenha essas telas primeiro. Depois o **front-end** constrói a versão web, e o **mobile**, o app. As duas versões conversam com **a mesma API**.

## A API (back-end)

O back-end oferece o "cardápio" de pedidos que o front e o app podem fazer:

| Pedido | O que faz |
| --- | --- |
| `GET /api/salas` | lista as salas |
| `GET /api/salas/backend/mensagens` | busca as últimas mensagens da sala |
| `POST /api/salas/backend/mensagens` | manda uma mensagem nova |
| `DELETE /api/mensagens/42` | apaga uma mensagem (só se for sua!) |

E aplica as **regras de negócio**: precisa estar logado para mandar mensagem, mensagem não pode ser vazia, só o autor (ou um líder) pode apagar.

### Tempo real: o WebSocket

Num chat, a mensagem do colega precisa aparecer **na hora**, sem você recarregar a página. O HTTP comum é "pergunta e resposta": o servidor só fala quando é perguntado. Para o tempo real, usamos o **WebSocket**: uma conexão que **fica aberta**, e o servidor pode avisar "chegou mensagem nova!" a qualquer momento.

## Os dados (banco de dados)

Um banco relacional organiza tudo em **tabelas**, como planilhas que se ligam:

```sql
CREATE TABLE usuarios (
  id SERIAL PRIMARY KEY,
  github VARCHAR(40) NOT NULL,
  nome VARCHAR(80)
);

CREATE TABLE salas (
  id SERIAL PRIMARY KEY,
  nome VARCHAR(40) NOT NULL
);

CREATE TABLE mensagens (
  id SERIAL PRIMARY KEY,
  sala_id INT REFERENCES salas(id),
  autor_id INT REFERENCES usuarios(id),
  texto TEXT NOT NULL,
  enviada_em TIMESTAMP DEFAULT NOW()
);
```

Cada mensagem "aponta" para a sala e para o autor dela. Buscar as mensagens de uma sala vira uma consulta:

```sql
SELECT texto, enviada_em FROM mensagens WHERE sala_id = 3 ORDER BY enviada_em DESC LIMIT 50;
```

## Testes (QA) e publicação (DevOps)

- **QA** escreve os casos de teste: mandar mensagem vazia, mandar 5 mil caracteres, perder a internet no meio, duas pessoas apagando a mesma mensagem...
- **DevOps** monta o caminho automático: a cada PR, os testes rodam; quando entra na `main`, a nova versão vai para o ar sozinha. E monitora: se o servidor cair às 3 da manhã, alguém fica sabendo.
